# 서빙 설계 — 모델과 백엔드의 계약

2026-07-27 · 레인 A(모델) ↔ 레인 B(서비스) 경계 문서 · 코드: `service/precompute.py`(A) · `service/api.py`·`app.py`(B)

**확정: 2026-07-27, 레인 C 검토 완료.** 검토에서 더한 것 3건 — §2-신규 키의 B→C JSON 형식, §3의 UI 대체 표기(프론트 반영 완료), §7의 404 소비자 의무. 이 문서 기준으로 백엔드 구현을 진행한다.

이 문서가 정하는 것은 **무엇이 언제 계산되고, 누가 쓰고, 무엇을 절대 하면 안 되는가**다. 모델 내부(피처·하이퍼파라미터)는 `model-findings.md`가, 화면 문구는 `ui-data-contract.md`가 맡는다.

## 1. 경계 — 요청 시에는 모델을 부르지 않는다

```
[배치 · 레인 A]                          [요청 시 · 레인 B]
model.dataset  스플릿 구축 (약 6분)
model.train    적합                        없음
service.precompute  격자 × 업태 점수        grid_score 조회
     ↓ kb.db                                score_meta 조회
grid_score 229,356행                       + 사용자 입력으로 산식 계산
score_meta   k/v                           (economics · goodwill)
```

**API는 모델을 적합하지도, 호출하지도 않는다.** `model.recommend`는 학습셋을 다시 만들고 21,544격자를 채점하므로 수 분이 걸린다. 요청 경로에 들어가면 안 된다. 배치가 미리 다 계산해 테이블에 넣고, API는 **조회 + 산술**만 한다.

이 경계를 지키는 실질적 장치: **`service/` 전체(단 `precompute.py` 제외)에 `model.*` import가 없어야 한다.** import가 생기는 순간 무거운 것이 요청 경로로 새고 있다는 신호다. (2026-07-27 확장 — 당초 검사 범위가 `api.py`뿐이어서 `economics.py`로 샌 모델 적합을 못 잡았다. 실제로 첫 `/economics`가 51초간 LightGBM을 학습했고, 수리로 곡선을 배치 산출물로 옮겼다: `lanes/B-backend.md` B-002.)

## 2. 배치가 만드는 것

### `grid_score` — 격자 × 업태 점수판

| 컬럼 | 의미 |
|---|---|
| `uptae` | 업태 12종 |
| `grid_id` | 100m 격자 (`gx_gy`, EPSG:5179 기준) |
| `score` | 모델 원확률 — **화면에 내보내지 않는다**(§4) |
| `grade` | 1(최상) ~ 10 |
| `observed` | **그 등급에서 실제로 관측된 3년 생존율** — 화면이 쓰는 값 |

229,356행 = 12업태 × 19,113격자. 21,544개 중 이웃 이력 20건 미만인 2,431개는 **의도적으로 빠진다** — 이력이 없는 칸이 "실패 기록이 없어서" 좋게 랭크되는 것이 이 도구가 할 수 있는 가장 나쁜 거짓말이다. 빠진 격자는 "평가 불가"로 응답해야지 나쁜 등급으로 응답하면 안 된다.

**스키마를 바꾸려면 레인 B에 먼저 알린다.** 모델 내부는 자유롭게 바꿔도 된다.

### `score_meta` — k/v

API가 실제로 읽는 6키가 **계약**이다. 이름이 어긋나면 값이 조용히 `null`이 된다(2026-07-27에 실제로 발생).

| 키 | 형식 | 소비처 |
|---|---|---|
| `as_of` | `2026-07` | 응답 헤더 |
| `observed_by_grade` | 쉼표 10개 | 등급별 생존율 |
| `observed_by_grade_n` | 쉼표 10개 | 표본수 |
| `observed_by_grade_ci_low` / `_ci_high` | 쉼표 10개 | 95% 신뢰구간 |
| `overall_survival` | 실수 | 비교 기준선 |

**같은 값을 두 모양으로 쓰지 않는다.** 점추정·구간·표본수는 전부 같은 십분위 세그먼트 계산에서 한 번에 나온다.

계보 추적용으로 함께 기록하되 API가 안 읽는 키: `rank_model`(배포 모델명) · `rank_features`(순위 피처 목록). **DB만 보고 어떤 계보로 계산됐는지 확인할 수 있어야** 문서와 배포가 갈라졌을 때 잡을 수 있다.

### 아직 API가 노출하지 않는 키 (레인 B 작업 대상)

라운드 4에서 추가했고 소비처가 없다:

| 키 | 내용 | 화면 용도 |
|---|---|---|
| `observed_by_gradeband_{1,3,5}y` | 등급밴드 3 × `생존율:CI하한:CI상한:표본수` | 기간별 생존 곡선 |
| `overall_survival_{1,3,5}y` · `test_window_{1,3,5}y` · `bench_{1,3,5}y` | 각 곡선의 분모·검증창·벤치 | 곡선 라벨 |
| `gradeband_labels` · `area_bands` · `observed_by_grade_area` | 등급밴드 3 × 면적 5구간 교차표 | "이 자리에 얼마짜리 가게" |
| `grade_area_bench` | 교차표가 어느 벤치 값인지 | 캡션 |

**B→C JSON 형식 (확정 — `GET /meta` 응답에 추가, camelCase·비율 0..1 관례 유지):**

```ts
// 기간별 실측 생존. 1·3년은 같은 코호트라 한 곡선으로 이어도 되고,
// 5년은 별도 코호트(2019–2021)라 구조적으로 분리해 실어 잇지 못하게 한다(§5-5).
survivalByPeriod: {
  years: 1 | 3 | 5;
  cohort: string;            // 예: "2023" / "2019-2021 (코로나기)"
  testWindow: string;        // test_window_{n}y
  overall: number;           // overall_survival_{n}y
  bench: string;             // bench_{n}y
  bands: { band: string; survival: number; ciLow: number | null;
           ciHigh: number | null; n: number | null }[];
}[];

// 등급밴드 × 면적 교차표. 관측이 없는 칸은 null 유지(0 금지, §5-2).
gradeArea: {
  gradeBands: string[];      // gradeband_labels
  areaBands: string[];       // area_bands
  survival: (number | null)[][];  // [band][areaBand]
  bench: string;             // grade_area_bench
} | null;                    // 키 자체가 없으면 null — 화면은 해당 카드를 그리지 않는다
```

## 3. 등급 알고리즘 — 두 단계, 둘 다 오해하기 쉽다

### 점수 → 등급: **홀드아웃 십분위의 절대 경계**

배치는 검증 코호트(2023년 개업)를 점수순으로 10등분해 **경계값 10개**를 얻고, 현재 시점 격자의 점수를 그 경계에 태운다.

**현재 격자를 10%씩 자르는 것이 아니다.** 그래서 업태마다 1등급 격자 수가 다르다. 이건 버그가 아니라 설계다 — 등급은 "그 점수대의 자리에서 실제로 관측된 생존율"을 가리키므로 경계가 고정돼야 의미가 있다. 매번 현재 분포를 10%로 자르면 상권이 나쁜 해에도 누군가는 1등급이 된다.

→ **UI에서 "상위 10%"는 1등급의 정확한 번역이 아니다.** "실측 생존율 75.5% 등급"이 정확하다.

**확정 표기 (레인 C 반영 완료)**: 등급 라벨은 `n등급`만 쓰고, 병기 숫자는 항상 그 등급의 실측 생존율이다 — 예: "1등급 · 실측 75%". "상위 n%" 계열 표현은 전 화면 금지어에 추가한다(`ui-spec.md` §4·§7 갱신).

### 등급 → 표시 숫자: **모델 확률이 아니라 실측 생존율**

모델의 원확률은 낙관 편향이 있다(학습기가 검증기보다 관대했다). 그래서 배치는 등급별로 **홀드아웃에서 실제로 관측된 생존율**을 계산해 `grid_score.observed`에 박고, API는 그 값을 낸다.

`score`는 **정렬 안정성 확인과 디버깅용**으로만 남긴다. 응답에 넣지 않는다.

## 4. 요청 시 계산되는 것 — 모델이 아니라 산식

### `economics` — 기대손익

```
기대 회수 = Σ_t  S(t) × 월순이익  −  초기투자
월순이익  = 월매출 × 마진 − 임대료
```

`S(t)`는 **등급별 실측 생존곡선**(가정한 곡선이 아니다). 곡선은 등급을 확정한 **동일 배치가 `score_meta.survival_curves_36m`으로 저장**하고(B-002), 요청 경로는 읽고 계보를 검증만 한다 — 없으면 합성하지 않고 503. 사용자 입력은 임대료·초기투자·마진·(선택)매출.

두 가지를 반드시 지킨다:

- **마진은 임대료 차감 전 값**(기본 25%). 공표 음식점업 영업이익률(10~15%)은 이미 임대료가 빠진 수치라 그대로 쓰고 임대료를 또 빼면 이중 차감이다. 첫 구현에서 멀쩡한 조건이 월 33만원 적자로 나와 발견했다.
- **마진 가정이 결과를 지배한다.** 마진 20/25/30%에서 상위·중간·하위 **세 등급 모두 부호가 뒤집힌다**(−3,427만 ↔ +3,584만). 단일 숫자로 보여주면 안 되고, 세 칸 전부 "가정에 민감" 표기 대상이다.

### `goodwill` — 권리금 참고가

벤치마크는 **Level 4 (서울 전체 × 동일 업종)**로 고정한다. 동급 상권 군집화(E6)가 사전 등록 검증에 실패했기 때문이다(실루엣 0.1175 · η² 0.1327, 요구 0.25/0.20). 리포트에 **사용한 벤치마크 레벨을 표기**한다.

매출 데이터가 없는 격자(상권 밖 46.8%)는 **리포트를 만들지 않는다** — "무형재산을 계산할 매출 근거가 없습니다"로 응답한다. NULL을 서울 평균으로 채워 리포트를 만드는 것은 이 프로젝트가 금지한 목업이다.

## 5. 절대 하면 안 되는 것

각 항목은 실제로 사고가 났거나, 나면 조용히 거짓이 되는 지점이다.

1. **요청 경로에서 모델 적합.** `service/api.py`에 `model.*` import가 생기면 위반이다.
2. **NULL을 0으로 채우기.** 상권 밖 격자의 매출·유동인구는 NULL이다. 0을 넣으면 "최악의 입지"로 랭크된다. 없는 축은 `missing_axes`로 알린다.
3. **모델 원확률 노출.** 배포 모델의 Brier는 대안 모델보다 나쁘다 — 순위는 믿을 수 있어도 확률 절대값은 아니다. 등급과 실측치만 낸다.
4. **"상위 10%"라는 번역.** §3 참조.
5. **5년 곡선을 1·3년과 잇기.** 5년은 다른 코호트(2019–2021, 코로나기)의 별도 적합이라 하위10%가 3년 29.2% → 5년 32.6%로 **역전**한다. 2023 코호트의 5년 판정은 2028년에 나온다. 잇지 말고 별도 표기하거나 빼라.
6. **등급 × 면적 교차표를 인과로 제시.** 등급별 면적 분포가 다르고 면적은 자본력과 얽혀 있다. "그런 조건의 자리에서 실제로 이랬다"이지 "가게를 키우면 저 숫자가 된다"가 아니다.
7. **평가 대상 밖 격자를 나쁜 등급으로 응답.** "평가 불가"와 "나쁨"은 다르다.

## 6. 재계산이 필요한 시점

`service.precompute`를 다시 돌려야 하는 경우:

| 트리거 | 이유 |
|---|---|
| `model.train.DEPLOY` 변경 | 순위 피처가 바뀌면 점수 전부 무효 |
| `model.train.WINNER` 변경 | 배포 모델이 바뀌면 점수·등급 경계 전부 무효 |
| `CONFIRMED_TRAIN_YEARS` / `CONFIRMED_TEST_YEARS` 변경 | 등급 경계와 실측 생존율의 출처가 바뀜 |
| 인허가 데이터 재수집 | 격자 상태가 바뀜 |

**세 상수는 `model/train.py` 한 곳에만 있다.** `precompute`가 그걸 읽으므로, 문서 헤드라인과 배포 수치가 구조적으로 갈라질 수 없다. 상수를 바꾸고 precompute를 안 돌리는 것이 유일한 갈라짐 경로이며, 그건 `score_meta.rank_model`·`rank_features`를 확인하면 잡힌다.

소요: 약 2분(모델 적합 + 21,544격자 상태 계산 + 12업태 채점).

## 7. 실패 모드와 응답

| 상황 | 응답 |
|---|---|
| `grid_score` 비어 있음 | 503 — 배치 미실행. 빈 배열로 200을 주지 않는다 |
| `score_meta` 키 누락 | 해당 필드만 `null`, 나머지는 정상 응답. **단 `observed_by_grade`가 없으면 503** — 등급 숫자가 없으면 화면이 거짓말한다 |
| 요청 격자가 평가 대상 밖 | 404 + `detail`이 정확히 `"이웃 이력 부족으로 평가하지 않음"`으로 시작 — 프론트가 이 문자열로 분기한다 |
| 상권 밖 격자의 매출 조회 | 200 + `missing_axes`에 명시. NULL을 채우지 않는다 |
| 뷰포트가 너무 넓음 | 413 — 격자 상한 초과 |

**소비자(레인 C) 의무**: 404 "평가 대상 밖"은 오류 상태(재시도 버튼)로 그리지 않는다 — "평가 불가"는 실패가 아니라 정답이므로 전용 상태("이 격자는 평가하지 않았습니다 — 주변 개업 이력 부족")로 렌더한다. §5-7("평가 불가 ≠ 나쁨")의 화면 측 이행이다.
