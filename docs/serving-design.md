# 서빙 설계 — 모델과 백엔드의 계약

2026-07-27 · 레인 A(모델) ↔ 레인 B(서비스) 경계 문서 · 코드: `service/precompute.py`(A) · `service/api.py`·`app.py`(B)

**확정: 2026-07-27, 레인 C 검토 완료.** 검토에서 더한 것 3건 — §2-신규 키의 B→C JSON 형식, §3의 UI 대체 표기(프론트 반영 완료), §7의 404 소비자 의무. 이 문서 기준으로 백엔드 구현을 진행한다.

이 문서가 정하는 것은 **무엇이 언제 계산되고, 누가 쓰고, 무엇을 절대 하면 안 되는가**다. 모델 내부(피처·하이퍼파라미터)는 `model-findings.md`가, 화면 문구는 `ui-data-contract.md`가 맡는다.

---

## 1. 경계 — 요청 시에는 모델을 부르지 않는다

```
[배치 · 레인 A]                          [요청 시 · 레인 B]
model.dataset  스플릿 구축 (약 6분)
model.train    적합                        없음
service.precompute  격자 × 업태 점수        grid_score 조회
     ↓ kb.db                                score_meta 조회
grid_score 241,776행                       + 사용자 입력으로 산식 계산
score_meta   k/v                           (economics · goodwill)
```

**API는 모델을 적합하지도, 호출하지도 않는다.** `model.recommend`는 학습셋을 다시 만들고 23,573격자 상태를 계산하므로 수 분이 걸린다. 요청 경로에 들어가면 안 된다. 배치가 미리 다 계산해 테이블에 넣고, API는 **조회 + 산술**만 한다.

이 경계를 지키는 실질적 장치: **`service/` 전체(단 `precompute.py` 제외)에 `model.*` import가 없어야 한다.** import가 생기는 순간 무거운 것이 요청 경로로 새고 있다는 신호다. (2026-07-27 확장 — 당초 검사 범위가 `api.py`뿐이어서 `economics.py`로 샌 모델 적합을 못 잡았다. 실제로 첫 `/economics`가 51초간 LightGBM을 학습했고, 수리로 곡선을 배치 산출물로 옮겼다: `lanes/B-backend.md` B-002.)

## 2. 배치가 만드는 것

### `grid_score` — 격자 × 업태 점수판

| 컬럼 | 의미 |
|---|---|
| `uptae` | 업태 12종 |
| `grid_id` | 100m 격자 (`gx_gy`, EPSG:5179 기준) |
| `score` | 모델 원확률 — **화면에 내보내지 않는다**(§4) |
| `grade` | 1(최상) ~ 9 |
| `observed` | **그 등급에서 실제로 관측된 3년 생존율** — 화면이 쓰는 값 |

241,776행 = 12업태 × 20,148격자. 23,573개 중 이웃 이력 20건 미만인 3,425개는 **의도적으로 빠진다** — 이력이 없는 칸이 "실패 기록이 없어서" 좋게 랭크되는 것이 이 도구가 할 수 있는 가장 나쁜 거짓말이다. 빠진 격자는 "평가 불가"로 응답해야지 나쁜 등급으로 응답하면 안 된다.

**스키마를 바꾸려면 레인 B에 먼저 알린다.** 모델 내부는 자유롭게 바꿔도 된다.

### `score_meta` — k/v

API가 실제로 읽는 6키가 **계약**이다. 이름이 어긋나면 값이 조용히 `null`이 된다(2026-07-27에 실제로 발생).

| 키 | 형식 | 소비처 |
|---|---|---|
| `as_of` | `2026-07` | 응답 헤더 |
| `observed_by_grade` | 쉼표 9개 | 등급별 생존율 |
| `observed_by_grade_n` | 쉼표 9개 | 표본수 |
| `observed_by_grade_ci_low` / `_ci_high` | 쉼표 9개 | 95% 신뢰구간 |
| `overall_survival` | 실수 | 비교 기준선 |

**같은 값을 두 모양으로 쓰지 않는다.** 점추정·구간·표본수는 전부 같은 9등급 세그먼트 계산에서 한 번에 나온다.

계보 추적용으로 함께 기록하되 API가 안 읽는 키: `rank_model`(배포 모델명) · `rank_features`(순위 피처 목록). **DB만 보고 어떤 계보로 계산됐는지 확인할 수 있어야** 문서와 배포가 갈라졌을 때 잡을 수 있다.

### 아직 API가 노출하지 않는 키 (레인 B 작업 대상)

라운드 4에서 추가했고 소비처가 없다:

| 키 | 내용 | 화면 용도 |
|---|---|---|
| `observed_by_gradeband_{1,2,3,5}y` | 등급밴드 3 × `생존율:CI하한:CI상한:표본수` | 기간별 생존 곡선 |
| `overall_survival_{1,2,3,5}y` · `test_window_{1,2,3,5}y` · `bench_{1,2,3,5}y` | 각 곡선의 분모·검증창·벤치 | 곡선 라벨 |
| `gradeband_labels` · `area_bands` · `observed_by_grade_area` | 등급밴드 3 × 면적 5구간 교차표 | "이 자리에 얼마짜리 가게" |
| `grade_area_bench` | 교차표가 어느 벤치 값인지 | 캡션 |

**B→C JSON 형식 (확정 — `GET /meta` 응답에 추가, camelCase·비율 0..1 관례 유지):**

```ts
// 기간별 실측 생존. 1·2·3년은 같은 코호트라 한 곡선으로 이어도 되고,
// 5년은 별도 코호트(2019–2021)라 구조적으로 분리해 실어 잇지 못하게 한다(§5-5).
survivalByPeriod: {
  years: 1 | 2 | 3 | 5;
  cohort: string;            // 예: "2023" / "2019-2021 (코로나기)"
  testWindow: string;        // test_window_{n}y
  overall: number;           // overall_survival_{n}y
  bench: string;             // bench_{n}y
  bands: { band: string; survival: number; ciLow: number | null;
           ciHigh: number | null; n: number | null }[];
}[];

// 등급밴드 × 면적 교차표. 관측이 없는 칸은 null 유지(0 금지, §5-2).
gradeArea: {
  gradeBands: string[];      // gradeband_labels
  areaBands: string[];       // area_bands
  survival: (number | null)[][];  // [band][areaBand]
  bench: string;             // grade_area_bench
} | null;                    // 키 자체가 없으면 null — 화면은 해당 카드를 그리지 않는다
```

## 3. 등급 알고리즘 — 두 단계, 둘 다 오해하기 쉽다

### 점수 → 등급: **홀드아웃 내신형 9등급의 절대 경계**

배치는 검증 코호트(2023년 개업)를 점수순으로
`4-7-12-17-20-17-12-7-4%`의 9구간으로 나눠 **경계값 9개**를 얻고,
현재 시점 격자의 점수를 그 경계에 태운다. 등분위10·정규형10·내신형9
세 모양을 결과 전에 고정해 비교했고, 가운데 역전 해소와 꼬리 표본
317건 확보를 근거로 내신형9를 골랐다.

**현재 격자를 위 비율로 다시 자르는 것이 아니다.** 그래서 업태마다 1등급
격자 수가 다르다. 이건 버그가 아니라 설계다 — 등급은 "그 점수대의 자리에서
실제로 관측된 생존율"을 가리키므로 경계가 고정돼야 의미가 있다. 매번 현재
분포를 다시 자르면 상권이 나쁜 해에도 누군가는 1등급이 된다.

→ **UI에서 "상위 n%"는 1등급의 정확한 번역이 아니다.** "1등급 · 실측
80.1%"가 정확하다. 2026-07-31 원천 갱신분의 양끝 격차는 70.0%p이고
홀드아웃 AUC는 0.6383이다. §28의 구간 선택 당시 69.1%p·0.6369와 달라진
이유는 경계를 바꾼 것이 아니라 인허가 원천과 적합 결과가 갱신됐기 때문이다.

**확정 표기 (레인 C 반영 완료)**: 등급 라벨은 `n등급`만 쓰고, 병기 숫자는 항상 그 등급의 실측 생존율이다 — 예: "1등급 · 실측 80.1%". "상위 n%" 계열 표현은 전 화면 금지어에 추가한다(`ui-spec.md` §4·§7 갱신).

### 등급 → 표시 숫자: **모델 확률이 아니라 실측 생존율**

모델의 원확률은 낙관 편향이 있다(학습기가 검증기보다 관대했다). 그래서 배치는 등급별로 **홀드아웃에서 실제로 관측된 생존율**을 계산해 `grid_score.observed`에 박고, API는 그 값을 낸다.

`score`는 **정렬 안정성 확인과 디버깅용**으로만 남긴다. 응답에 넣지 않는다.

## 4. 요청 시 계산되는 것 — 모델이 아니라 산식

### `economics` — 기대손익

```
기대 회수 = Σ_t  S(t) × 월순이익  −  초기투자
월순이익  = 월매출 × 마진 − 임대료
```

`S(t)`는 **등급별 실측 생존곡선**(가정한 곡선이 아니다). 곡선은 등급을 확정한 **동일 배치가 `score_meta.survival_curves_36m`으로 저장**하고(B-002), 요청 경로는 읽고 계보를 검증만 한다 — 없으면 합성하지 않고 503. 사용자 입력은 임대료·초기투자·마진·(선택)매출.

두 가지를 반드시 지킨다:

- **마진은 임대료 차감 전 값**(기본 25%). 공표 음식점업 영업이익률(10~15%)은 이미 임대료가 빠진 수치라 그대로 쓰고 임대료를 또 빼면 이중 차감이다. 첫 구현에서 멀쩡한 조건이 월 33만원 적자로 나와 발견했다.
- **마진 가정이 결과를 지배한다.** 마진 20/25/30%에서 1등급은
  −3,278만 ↔ +3,961만, 5등급은 −3,875만 ↔ +2,449만으로 부호가
  뒤집힌다. 9등급은 −6,608만 ↔ −4,475만으로 전 구간 적자다.
  단일 숫자 대신 세 마진을 함께 보여주고, 부호가 바뀌는 1·5등급에는
  "가정에 민감"을 붙인다.

### `goodwill` — 권리금 참고가

벤치마크는 **Level 4 (서울 전체 × 동일 업종)**로 고정한다. 동급 상권 군집화(E6)가 사전 등록 검증에 실패했기 때문이다(실루엣 0.1175 · η² 0.1327, 요구 0.25/0.20). 리포트에 **사용한 벤치마크 레벨을 표기**한다.

매출 데이터가 없는 격자(상권 밖 49.5%)는 **리포트를 만들지 않는다** — "무형재산을 계산할 매출 근거가 없습니다"로 응답한다. NULL을 서울 평균으로 채워 리포트를 만드는 것은 이 프로젝트가 금지한 목업이다.

### `estimate` · `compare` — 실질 월 점유비용

보증금·월세·권리금은 형태만 다른 같은 자리값이다. 한 달치로 환산하면 순위가
뒤집힌다.

```
실질 월 점유비용 = 월세 + 관리비
                 + 보증금 × opportunityRate ÷ 12          (돌려받으므로 이자만)
                 + 권리금 × (1 − 승계확률) ÷ horizonMonths
```

`승계확률`은 M2 모델의 격자별 값이다(`succession_score`). **회수율이 아니다** —
다음 사람이 그 자리를 이어받을 확률이지, 낸 권리금을 그만큼 돌려받는다는 뜻이
아니다. 지불비율 원천이 공개돼 있지 않아 대표값은 `승계확률 = 0`, 즉 한 푼도 못
건지는 쪽으로 잡는다.

불확실성 밴드는 세 축을 흔든 최대 27조합의 5~95 백분위다.

```
승계확률 {0, p/2, p}             p = 격자 승계확률 (없으면 {0} 하나)
상각기간 {N−12, N, N+12}개월      N = horizonMonths, 하한 1
이자율   {r−0.01, r, r+0.01}      r = opportunityRate, 하한 0
```

각 축은 집합이라 하한에 걸리면 원소가 줄고 조합도 그만큼 줄어든다.

**밴드 폭 자체가 정보다.** 권리금 0 인 자리는 폭이 몇 만원이고(가정을 바꿔도
결과가 같다), 권리금이 큰 자리는 폭이 백만 단위다(같은 «싸다»가 베팅이다).

산식은 `service/cost.py` 의 순수 함수이고 화면은 다시 계산하지 않는다. 두 곳에서
계산하면 반올림만 어긋나도 화면과 리포트가 다른 숫자를 말한다.

## 5. 절대 하면 안 되는 것

각 항목은 실제로 사고가 났거나, 나면 조용히 거짓이 되는 지점이다.

1. **요청 경로에서 모델 적합.** `service/` 전체(단 `precompute.py` 제외)에 `model.*` import가 생기면 위반이다 — §1의 확장된 범위와 같다. `api.py`만 보다가 `economics.py`로 샌 적합을 놓친 적이 있다.
2. **NULL을 0으로 채우기.** 상권 밖 격자의 매출·유동인구는 NULL이다. 0을 넣으면 "최악의 입지"로 랭크된다. 없는 축은 `missing_axes`로 알린다.
3. **모델 원확률 노출.** 배포 모델의 Brier는 대안 모델보다 나쁘다 — 순위는 믿을 수 있어도 확률 절대값은 아니다. 등급과 실측치만 낸다.
4. **"상위 10%"라는 번역.** §3 참조.
5. **5년 곡선을 1·2·3년과 잇기.** 5년은 다른 코호트(2019–2021, 코로나기)의 별도 적합이다. 2023 코호트의 5년 판정은 2028년에 나온다. 잇지 말고 별도 표기하거나 빼라.
6. **등급 × 면적 교차표를 인과로 제시.** 등급별 면적 분포가 다르고 면적은 자본력과 얽혀 있다. "그런 조건의 자리에서 실제로 이랬다"이지 "가게를 키우면 저 숫자가 된다"가 아니다.
7. **평가 대상 밖 격자를 나쁜 등급으로 응답.** "평가 불가"와 "나쁨"은 다르다.
8. **검색 트렌드·점포 언급량을 어떤 형태로도 노출.** 예측에 안 쓰는 것은 이미 확정됐고, **"참고 정보"로도 못 쓴다** — §9-A 참조.
9. **"뜨는 상권" 기능을 만들기.** 선행성을 주장하려면 입증이 필요한데 실패했다 — §9-B 참조.

## 6. 재계산이 필요한 시점

`service.precompute`를 다시 돌려야 하는 경우:

| 트리거 | 이유 |
|---|---|
| `model.train.DEPLOY` 변경 | 순위 피처가 바뀌면 점수 전부 무효 |
| `model.train.WINNER` 변경 | 배포 모델이 바뀌면 점수·등급 경계 전부 무효 |
| `CONFIRMED_TRAIN_YEARS` / `CONFIRMED_TEST_YEARS` 변경 | 등급 경계와 실측 생존율의 출처가 바뀜 |
| 인허가 데이터 재수집 | 격자 상태가 바뀜 |

**세 상수는 `model/train.py` 한 곳에만 있다.** `precompute`가 그걸 읽으므로, 문서 헤드라인과 배포 수치가 구조적으로 갈라질 수 없다. 상수를 바꾸고 precompute를 안 돌리는 것이 유일한 갈라짐 경로이며, 그건 `score_meta.rank_model`·`rank_features`를 확인하면 잡힌다.

소요: 약 2분(모델 적합 + 23,573격자 상태 계산 + 12업태 채점).

| 상황 | 응답 |
|---|---|
| `grid_score` 비어 있음 | 503 — 배치 미실행. 빈 배열로 200을 주지 않는다 |
| `score_meta` 키 누락 | 해당 필드만 `null`, 나머지는 정상 응답. **단 `observed_by_grade`가 없으면 503** — 등급 숫자가 없으면 화면이 거짓말한다 |
| 요청 격자가 평가 대상 밖 | 404 + `detail`이 정확히 `"이웃 이력 부족으로 평가하지 않음"`으로 시작 — 프론트가 이 문자열로 분기한다 |
| 상권 밖 격자의 매출 조회 | 200 + `missing_axes`에 명시. NULL을 채우지 않는다 |
| 뷰포트가 너무 넓음 | 413 — 격자 상한 초과 |

**소비자(레인 C) 의무**: 404 "평가 대상 밖"은 오류 상태(재시도 버튼)로 그리지 않는다 — "평가 불가"는 실패가 아니라 정답이므로 전용 상태("이 격자는 평가하지 않았습니다 — 주변 개업 이력 부족")로 렌더한다. §5-7("평가 불가 ≠ 나쁨")의 화면 측 이행이다.

## 9. 라운드 5(비정형 검정)가 백엔드에 남기는 것

`docs/model-findings.md` §11 · 사전 등록 `docs/unstructured-plan.md` §E.
결론은 "비정형을 안 쓴다"가 아니라 **"안 쓰는 이유를 알고, 그 이유가 제품
결정을 바꾼다"**이다.

### 9-A. `trend`·`mention` 은 실험 자산이지 제품 데이터가 아니다

DB에 남아 있다 — `trend` 27,848행 · `mention` 297,850행 · `mention_shop` 17,056행.
**재현을 위해 보존하는 것이며 서빙 경로에 들어가면 안 된다.**

예측에 기여하지 않는다는 것은 §6·§6-B·§8-G에서 세 번 확인됐다. 그런데 §6이
결론 안에 *"상권 부상 감지나 맥락 정보로는 여전히 유효할 수 있다"* 는 여지를
남겨뒀고, **§11-E가 그 여지를 닫았다**:

```
검색 관심도 vs 실제 유동인구   Spearman ρ = +0.079   CI [−0.071, +0.218]  (n=213)
관심도 상위 절반 유동인구 중앙값 1,010,354 · 하위 절반 1,084,153
```

검색량은 "이 동네 이름이 얼마나 검색되는가"이지 "이 동네에 얼마나 오는가"가
아니다. **실제 인파를 반영하지 않는 숫자를 "참고 정보"라고 화면에 올릴 수 없다.**
올리는 순간 사용자는 그것을 근거로 쓴다.

**트립와이어**: `service/` 어디에도 `trend`·`mention`·`mention_shop` 테이블
참조가 없어야 한다.

```bash
grep -rn "trend\|mention" service/*.py     # 기대: 0건 (2026-07-27 확인 완료)
```

### 9-B. "뜨는 상권"을 만들지 않는다 — 스코프 방어

서울시 상권분석서비스가 이미 제공한다(점포수·매출·유동인구·주거인구의 전분기
대비 순위). **전부 후행지표다.** 우리가 같은 화면을 만들 이유는 "우리는 선행
지표다"라고 말할 수 있을 때뿐인데, 그 주장을 뒷받침할 실험이 **둘 다 실패했다**:

| 실험 | 결과 |
|---|---|
| B2 — 검색 관심도 → 상권 성장 | CV R² 증분 +0.0003 · 위약 p=0.350 → 기각 |
| D1 — 업종 구성 변화 → 성장 (Glaeser 한국판) | 40컨셉 FDR 통과 0개 → 기각 |

그리고 C1이 덧붙인다: 예측력 증분에서 **정형(지하철 승하차 +0.0055)이
비정형(트렌드 +0.0003)을 18배 앞선다.** 비정형으로 만들 이유가 없다.

**따라서 이 제품은 "지금 이 자리가 어떤가"만 답한다.** "앞으로 뜰 동네"는
답하지 않는다. 이것은 기능 누락이 아니라 **입증 실패에 대한 정직한 대응**이며,
UI 카피에서도 "유망/뜨는/전망" 류의 표현을 쓰지 않는다.

### 9-C. `shop_concept` — 기본값은 **노출하지 않음**

라운드 5가 만든 새 자산이다(477,361행, 업태 "한식" 22만 건을 곱창·족발·칼국수·
포차·양꼬치 등으로 분리). 시대 누수 관문을 통과했고(macro-F1 0.1820) 군집
품질도 좋다. **그러나 D1에서 컨셉 구성 변화는 지역 성장을 예측하지 못했다.**

| 쓸 수 있는 것 | 쓸 수 없는 것 |
|---|---|
| 순수 사실 카운트 — "이 반경에 곱창집 N곳" (참/거짓이 명확) | 등급에 반영됐다는 암시 |
| | "이 컨셉이 유망하다" 류의 서술 |
| | 컨셉별 추천·정렬 |

**기본값은 미노출이다.** 근거는 두 가지다. 첫째, 화면에 올라간 숫자는 사용자가
자동으로 "추천에 반영된 것"으로 읽는다 — 검증되지 않은 것을 제품에 넣는 셈이
된다. 둘째, 반경 내 동업종 경쟁은 이미 `same_uptae_cnt`·`same_uptae_r1`이
등급 안에서 처리하고 있어 **새 정보가 아니다.**

넣는다면 조건은 셋이다: (1) 등급과 시각적으로 분리된 영역, (2) "경쟁 현황"
같은 사실 라벨, (3) 등급 산출과 무관하다는 명시. 셋 다 충족하지 못하면 넣지
않는다.

### 9-D. `past_inflow` 는 발견이지만 **제품에 쓰지 않는다**

B2에서 과거 개업 유입률이 미래 개업 유입을 강하게 설명했다
(계수 +0.0693, 클러스터 CI [+0.0466, +0.1565] — 0을 확실히 배제). 트렌드·승하차
어느 쪽보다 크다.

**그래도 쓰지 않는다.** 세 가지 이유다:

1. **사전 등록된 검정 대상이 아니었다.** B2의 통제 변수였다. 부산물을 결과처럼
   쓰면 그것이 바로 §8-G가 경고한 사후 선택이다.
2. **자기상관이지 "유망함"이 아니다.** "개업이 많던 곳에 개업이 많다"는 문장은
   창업자에게 아무것도 알려주지 않는다. 생존을 말하지 않기 때문이다.
3. **이미 등급 안에 있다.** `openings_36m`·`growth_36m`·`open_accel`이 같은
   정보를 as-of로 처리한다.

### 9-E. 배제한 신호를 제품 자산으로 — `excluded_signals`

"왜 검색 트렌드를 안 쓰나?"는 심사위원과 사용자 모두에게 자연스러운 질문이고,
**답이 준비되어 있는 것 자체가 신뢰의 근거**다. 지금은 그 답이 문서에만 있다.

제안: `meta` 응답에 상수 배열 하나를 추가한다. **새 계산이 없다** — 실험 결과를
문자열로 굳힌 것이며, 재계산 트리거(§6)에도 걸리지 않는다.

```
excluded_signals: [
  { signal: "검색 트렌드",     measured: 4, reason: "예측 기여 없음 + 실제 유동인구와 상관 0.08" },
  { signal: "점포 블로그 언급량", measured: 1, reason: "예측 기여 없음 (점 단위로 내려도 동일)" },
  { signal: "리뷰 감성",       measured: 0, reason: "과거 리뷰 아카이브 부재로 as-of 검증 불가 + 점포 속성이지 입지가 아님" },
  { signal: "유동인구·혼잡도",  measured: 0, reason: "시계열 부재(상권 통계는 1개 분기 스냅샷) — as-of 불가" },
]
```

`measured` 는 **실제로 검정한 횟수**다. 0은 "안 해봤다"가 아니라 **"데이터 구조상
검증이 불가능하다"**이며, 이 구분을 문구에서 지우지 않는다.

**레인 B 작업 크기**: `meta()` 응답에 정적 키 1개. 파싱·스키마만 늘고 DB 조회는
늘지 않는다.

## 10. §J-1 `visitorParty` — 예측과 분리한 표기 전용 관측

§J-1은 피처 채택이 아니라 화면 표기를 위한 별도 검정이다. 통과한 클래스는
`family`와 `work` 뿐이다(파일럿 정밀도 0.633 · 0.700). **2026-08-01 부터 화면은 이
정확도를 병기하지 않는다** — 60→100 글 재수집에서 코퍼스 일부가 다른 추출기로
라벨돼 파일럿 값이 전체를 설명하지 못하게 됐다(§J-1 재판정). `precision` 은 응답에
그대로 실려 있으므로 단일 라벨러로 재검정하면 서버 변경 없이 되살릴 수 있다.
`alone`·`couple`·`friend`는 기각됐고 DB에 있어도 서빙하지 않는다.

값은 블로그를 쓴 **방문객 관점**의 상권 단위 관측이다. 같은 상권 안 격자는 같은
값을 받고, 등급·점수·추천 순위에는 사용하지 않는다. 응답 키는 `visitorParty`,
`resolutions.visitorParty`는 `"상권"`이다.

**비정형 예측 검정 누계 13건 · 채택 0 은 그대로다.** 이것은 표기 문턱의 통과이지
피처 문턱의 통과가 아니다.

## 11. `salesMix` — 「가게 수」와 「결제」를 갈라 놓는 카드

`conceptMix`(상호명으로 센 영업중 점포 구성)의 짝이다. 상권의 업종별 카드 결제
구성을 최신 분기 하나로 낸다. 응답 키 `salesMix`, `resolutions.salesMix`는
`"상권 (중앙값 반경 151m)"`이고, 상권 밖(격자의 49.5%)은 `available=false`다.

**왜 둘 다 내는가.** 상권 1,185곳에서 재보니 두 값은 같지 않다 — 커피는 가게
27.8% / 결제 24.7%, 한식은 가게 31.8% / 결제 55.1%다. 가게 수로 업종 수요를
짐작하면 이만큼 틀린다.

**섞지 않는다.** 두 값을 가중 평균하면 실제 결제 구성과의 적합이 오르지만
(a=0.7 에서 r 0.665→0.699), 구성 오차 자체는 41.2%→41.1%로 움직이지 않고
결과물이 «무엇을 센 값»도 아니게 된다. 각각 무엇을 센 것인지 말할 수 있는
상태로 나란히 둔다. 측정 근거는 `docs/unstructured-plan.md` §J-2.
