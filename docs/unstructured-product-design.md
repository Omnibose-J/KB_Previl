## 2. 왜 채택하는가

원안이 옳게 본 것은 **질문의 전환**이다. 아홉 번 기각된 것은 "비정형으로 예측할
수 있는가"였고, 원안은 "비정형이 관측한 사실을 그대로 보여줄 수 있는가"로 바꿨다.
후자는 검정 방식이 다르다 — 예측력이 아니라 **정확도와 재현성**만 물으면 된다.

무엇이 이 판정을 뒤집는가: **§4의 정밀도 검정.** `gripe` positive가 부정확하면
카드가 아니라 §17의 채택 하나를 재검토해야 한다.

## 3. 표시 단위 — 지명이 1차, 격자가 2차

원안은 §4.3에서 "업태별 1~5개"라고 정확히 적어놓고 §4.4에서 카드를 만들기로
갔다. 그 숫자대로면 사용자가 보는 후보 9개 중 8개에서 카드가 빈다.

| 단위 | `text_profile` 격자 | 상위 24 후보 (12업태) |
|---|---:|---:|
| 격자 r1 게이트 (원안) | 601 / 8,122 (7.4%) | 33 / 288 (11.5%) |
| **지명 게이트 (이 설계)** | **4,862 / 8,122 (59.9%)** | **148 / 288 (51.4%)** |

지명 게이트 = 그 지명에서 한 범주에 독립 점포 2곳 이상. 현재 판정된 73지명 중
**69지명(95%)이 통과**한다. 수집된 150지명을 전수 판정하면 더 오른다.

51.4%는 원안이 §10.2에 스스로 적어 둔 Phase 3 승격 조건("상위 20개 후보의 50%
이상")을 **단위 변경만으로** 충족한다.

### 규칙 3 위반이 아니다

`CLAUDE.md` 규칙 3은 거친 데이터를 격자로 배분하는 것을 금지하되, **"그 단위의
값으로 표기해 붙이는 것"은 허용**하고 순위 결정만 막는다. 이 카드는

- 지명 값을 지명 이름으로 표기한다 — `역삼동 일대에서 관측된 문제`
- 같은 지명의 격자는 같은 값을 본다 (동점)
- `grid_score`·순위·생존율에 들어가지 않는다

세 조건을 모두 지키므로 규칙 3이 허용하는 쪽이다. 카드 제목이 이미
`이 동네 운영 힌트`이고, §I-10-⑥이 지명을 검정 단위로 정했으므로 표현 단위를
지명으로 맞추면 검정과 표시가 같은 단위에서 만난다.

### 두 층으로 낸다

```
이 동네 운영 힌트 — 역삼동 일대
  주변에서 관측된 문제      ← 지명 집계. 4,862격자에서 뜬다
  이 자리 300m 안에서는     ← r1 집계. 601격자에서만 추가로 뜬다
```

지명만으로 충분하면 r1 블록은 생략한다. **r1 블록이 비었다고 "문제 없음"으로
읽히면 안 되므로** 표본 미달일 때는 블록 자체를 그린다.

## 4. 신호별 검정 상태

원안은 `gripe`를 Phase 1에, `guest`를 Phase 2에 뒀다. 저장된 검정 쌍을 다시
계산하면 **순서가 반대**다.

| 신호 | raw 일치 | κ | positive 밀도 | 상태 |
|---|---:|---:|---|---|
| `purpose` | 72.7% | **0.55** | 57~77% | 조건부 일치 89.4% · 구성비 차 ≤3.5pp |
| merit `fresh` | 98.7% | 0.77 | 3.0% | 신뢰 높으나 희소 |
| merit `kind` | 98.3% | 0.70 | 2.8% | 신뢰 높으나 희소 |
| merit `value` | 96.0% | 0.58 | 5.0% | 보통 |
| merit `portion` | 95.0% | 0.55 | 5.8% | 보통 |
| `party` | 82.0% | 0.46 | **10.7% vs 26.0%** | 판정자 간 2.4배 과태깅 |
| merit `mood` | 78.0% | 0.29 | 18.0% | 약함 |
| merit `taste` | 70.3% | 0.32 | 29.2% | 약함 |
| `gripe` 7범주 | 99.6% | **계산 불가** | 0.63% / 셀 | **positive 미검정** |

**`gripe`의 99.6%는 정보가 없다.** 300건 × 7범주 = 2,100셀에서 positive
기대값은 13.3셀이고 관측 불일치는 8.4셀이다. 불일치 규모가 positive 규모와 같은
자릿수라 "불만을 얼마나 재현하는가"는 측정된 적이 없다. κ로 확인하려 했으나
`verify2.py`가 쌍을 저장하지 않고 버려서 재계산이 불가능하다(→ C7).

**κ는 사후탐색이다.** §I-15·§I-17의 등록 판정은 raw ≥0.70 기준으로 통과했고
**그대로 둔다** — 결과를 본 뒤 기준을 조이는 것도 우회다(`CLAUDE.md` 규칙 6은
양방향이다). κ로 하는 일은 하나뿐이다: **무엇을 먼저 만들지 정하는 것.** 제품
우선순위는 검정 판정이 아니므로 사후 통계를 써도 된다.

`gripe`는 κ 문제가 아니라 **측정 공백**이다. 이건 재해석이 아니라 안 한 일이다.

### `purpose`는 비율로 낼 수 있다

두 판정자가 모두 값을 붙인 85건에서 일치 89.4%, 구성비는

| | Claude | gpt-4o-mini | 차 |
|---|---:|---:|---:|
| `meal` | 77.6% | 80.0% | 2.4pp |
| `cafe` | 14.1% | 10.6% | 3.5pp |
| `drink` | 8.2% | 9.4% | 1.2pp |

판정자를 바꿔도 최대 3.5pp다. **"비율 금지"를 전면 규칙으로 두지 않는다** —
`gripe_share`(점포 수 ÷ 판정 글 수, 분모가 사용자 기대와 다름)와 merit
`mood`/`taste`(비대칭 2~3배)가 금지 대상이지, 구성비가 안정한 항목까지 막을 근거는
없다. 규칙을 **"판정자 간 구성비 차 ≤5pp인 항목만 비율"**로 바꾼다.

무관 글 오염도 작다: 음식점 방문기가 아닌 34건 중 gpt가 맥락을 붙인 건 3건(9%)이다.
22.7%는 분모 부풀리기이지 오염이 아니라는 §I-15 결론과 같다.

### `party`는 보류한다 — 원안과 같은 결론, 다른 이유

원안은 "공식 계약이 `gripe`만 승인"을 근거로 들었으나 그건 `lanes/A-algorithm.md`
갱신 누락이었다(이 커밋에서 정정). 실제 보류 사유는 **밀도 편향**이다: gpt가
2.4배 많이 붙이므로 동행 비율을 그대로 내면 체계적으로 틀린다.

## 5. 검정 기준 개정 — `docs/unstructured-plan.md` §I-19 등록안

**아래를 판정 실행 전에 등록한다. 실행 후 등록은 무효다.**

```
§I-19 판정 신뢰도 기준 (2026-07-28 등록, §I-11~§I-18 재판정부터 적용)

1. raw 일치율 ≥ 0.70                       — 기존 §H-9-⑤ 유지
2. Cohen κ ≥ 0.40                          — 신규. 희소 범주에서 raw 를 보정한다
3. positive precision: 점추정 ≥ 0.70 이고
   Wilson 95% 하한 ≥ 0.50                  — 신규. 화면에 나가는 것은 positive 뿐이다
4. 비율 표시는 판정자 간 구성비 차 ≤ 5pp 인 항목만. 미달이면 목록으로만 낸다

세 기준을 모두 통과한 항목만 노출한다. 하나라도 미달이면 그 항목만 뺀다
(범주 단위 판정, §I-11 방식 유지).

검정 표본은 범주별 predicted-positive 총량이 정하며, 상한을 넘겨 등록하지
않는다. 등록 시점의 상한:
  wait 314 · price 297 · parking 171 · seat 164 · noise 73 · service 46 · clean 28
n < 30 인 범주(`clean`)는 전수 검수하고 Wilson 만으로 판정한다.

모든 재판정은 (1차 라벨, 2차 라벨, rowid_post) 쌍을 테이블에 저장한다.
저장하지 않은 검정은 통과해도 근거로 인용하지 않는다.
```

기존 판정(§I-11 · §I-13 · §I-17 · §I-18)은 **등록 당시 기준으로 통과한 채로
남는다.** §I-19는 소급하지 않는다.

## 6. 재판정 사양

크레딧 확보 후 실행한다. 세 신호가 모두 전수 데이터가 없거나(merit 0 · guest 0)
부분이거나(gripe 24,704/40,665 · 73지명/150) 옛 모델이다(demand_label = 4o-mini).

### 통합 1패스

지금은 신호마다 별도 패스라 3종 전수에 40,665 × 3 = 122k 호출이 든다. 한 글에
한 번 호출해 세 신호를 한 JSON으로 받으면 41k다.

```
model/judge_run.py          gripe + merit + guest 를 한 프롬프트로
  → judge_label(rowid_post, place, shop, <gripe 7>, <merit 6>, party, purpose,
                quote_json, target_shop, model, judged_at)
```

바뀌는 것 둘:

- **`quote_json`** — 범주별 근거 문장. `{"wait":"웨이팅 쩔구요","price":null}`.
  현재 `gripe_label.quote`는 글당 1개라 `price`와 `parking`이 같이 잡히면 같은
  문장이 두 범주에 실린다(실제로 `주차공간은 없었던것같구요`가 `price` 근거로
  저장돼 있다). 범주별 근거 없이는 evidence pack이 성립하지 않는다
- **`target_shop`** — 불만·칭찬의 대상이 `mgtno` 점포인지. 지금은 확인할 방법이
  없다

### 통합이 판정을 망치지 않는지 먼저 잰다

프롬프트가 길어지면 판정이 나빠질 수 있다. **파일럿 300건**을 기존 분리 판정과
같은 글에 대해 돌리고

- 신호별 raw 일치 ≥ 0.80 (통합 vs 분리)
- κ ≥ 0.60

미달이면 통합을 버리고 분리 패스로 간다. 이것도 §I-19와 함께 등록한다.

### 비용

**추정하지 않는다.** 파일럿 300건의 실제 토큰 사용량을 재고 40,665건으로
외삽한 뒤 실행 여부를 정한다. 지금 숫자를 적으면 근거 없는 수가 문서에 남는다.

### `demand_label`을 덮지 않는다

`demand_label`(4o-mini, 5,332건)은 §16 H-4 기각의 근거다. 새 판정은 별도
테이블에 쓴다. **§I-17의 `purpose` κ 0.55는 4o-mini 라벨에서 잰 값이므로,
nano로 재판정하면 그 검정은 무효가 되고 다시 재야 한다.**

## 7. 저장 설계

### 신규 — 지명 단위

```sql
CREATE TABLE text_place_profile (
  place        TEXT NOT NULL,
  signal       TEXT NOT NULL,     -- gripe | merit | purpose
  key          TEXT NOT NULL,     -- wait | taste | meal ...
  n_judged     INTEGER NOT NULL,  -- 이 지명의 판정 글 수 (분모)
  n_hit        INTEGER NOT NULL,
  n_shop       INTEGER NOT NULL,  -- 독립 점포 수. 게이트는 이 값이 정한다
  shops_json   TEXT,              -- 상위 8곳
  quotes_json  TEXT,              -- 범주별 근거 문장 (재판정 후에만 채운다)
  PRIMARY KEY (place, signal, key)
);
```

- `n_shop >= 2` 가 화면 게이트다. 1이면 저장하되 "이 동네의 문제"로 쓰지 않는다
- 격자→지명은 `grid_place`(21,529행, 지명 247개, `absa_post` 150지명을 모두 포함)
- **화면용 관측 요약이지 모델 피처가 아니다.** `grid_score`와 조인 금지

### 기존 — `text_profile` 유지

r1 2차 블록이 읽는다. 세 상태 계약은 `lanes/A-algorithm.md`에 적었다.

| 값 | 뜻 | 화면 |
|---|---|---|
| 행 없음 / `NULL` | r1 판정 글 10건 미만 | `근거 부족` |
| `""` | 충분히 봤는데 불만 없음 | `관측된 문제 없음` |
| `"wait:A\|B"` | 목록 있음 | 목록 |

원안 §7.2의 `null` vs `[]` 계약이 여기 그대로 대응한다.

### `score_meta` 선언 (이 커밋에서 정정 완료)

```
text_profile_gripe_judged_grids  5065   판정 충분
text_profile_gripe_listed_grids  3056   실제 목록 보유
text_profile_gripe_gate2_grids    601   한 범주 독립 점포 2곳 이상
```

## 9-B. 실제 상호명을 언제 내는가

원안은 evidence pack 확보 전까지 `경쟁점 A`로 익명화하자고 했다. **익명화하면
원안 스스로 §12에 적은 "일반 체크리스트처럼 보임" 위험이 현실이 된다** — 목록이
쓸모 있는 이유가 상호명이기 때문이다.

- 상호명 자체는 공공 인허가 데이터라 노출에 문제가 없다
- 문제는 **"이 가게는 대기 불만이 있다"는 부정적 연결**이다
- 따라서 게이트는 출처 추적이 아니라 **정밀도**다. PR 1에서 대상 점포 일치가
  확인된 범주만 실명으로 낸다
- 원문 인용·링크는 별개 문제다. 수집원 이용조건 확인 전까지 인용문을 화면에
  내지 않는다 (집계와 상호명은 가능)

익명 버전으로 사용자 검증을 통과해도 **실명 버전의 가치를 증명한 것이 아니다.**
검증한 형태와 출시할 형태를 같게 한다.
