## 1. 프로토타입 zip 패키징 — 미리 설계 안 하면 마감날 사고

| 문제 | 결정 |
|---|---|
| `kb.db` 445MB + `pipeline/cache/` 807MB는 gitignore — zip에 못 넣고, 넣어서도 안 됨 | **완료 (2026-07-30)** — `python -m service.demo_db --out kb-demo.db` 가 서빙 의존 14개 테이블만 추출한다. 실측 **267.6MB → zip 69.1MB**. `--audit` 이 `service/*.py` 를 스캔해 테이블 목록이 코드와 어긋나면 빌드를 거부하고, `--verify` 가 그 DB 로 API 를 띄워 meta·recommend·상세·건물 4경로를 확인한다(4/4 PASS). 제외된 큰 테이블은 `addr_tenancy`·`shop_concept`·`store` 로, 전부 파이프라인·모델 입력이며 서빙 리더가 없다 |
| `.env` API 키 — 절대 포함 금지 | `.env.example`만 동봉. 데모는 키 없이 돌아야 함(경량 DB 조회 + economics 산식은 키 불요. 지도 JS 키만 발급키 별도 안내) |
| 심사자가 파이프라인 전체를 재현할 수 없음 | README에 3단 구분: ① 데모 실행(경량 DB, 2분) ② 검증 재현(공개 API 키 필요, 캐시 없이 수 시간) ③ 전체 결과는 `docs/model-findings.md` 참조 |
| 심사 환경에서 실행 실패 리스크 | **화면 녹화 데모 영상(2~3분)을 zip에 동봉** — 실행이 안 돼도 심사가 가능하게. 본선(9/2 오프라인, 이대 ECC)도 로컬 실행(FastAPI+SQLite)이라 인터넷 불안정에 강함 |

**일정**: 8/1 패키징 리허설(깨끗한 환경에서 zip 풀고 데모 실행 — 리허설 없이 제출 금지) · 8/2 영상 녹화 + 최종 zip.

## 2. 기술설명서(PPT) — 기획안 서사를 그대로 쓰면 안 된다

`docs/기획안*.md`은 제안 시점 문서라 **이후 실측으로 반증된 주장**이 창의성 축에 들어 있다. 기술설명서가 기획안을 복사하면 심사 Q&A에서 무너진다. 교체 매핑:

| 기획안 주장 (쓰면 안 됨) | 실측 후 교체 서사 (이걸로) |
|---|---|
| "SNS 반응 = 매출 선행지표" (창의성 ①) | "비정형 기여를 **두 가지 방식으로 측정했고 둘 다 아니었다** — 측정 없이 결합을 주장하는 팀과 방법론적으로 다르다" + 절제표의 볼륨 vs 내용 행 |
| "정형+비정형 융합 한 점수" | "**홀드아웃 백테스트로 검증된 등급** — 상위 10% 실측 74.3% vs 하위 44.8%" |
| "예상 월매출 1,900만 / 생존확률 62%" (시나리오) | "확률 대신 **등급 + 실측 생존율**, 그리고 **입지 위험의 가격**(같은 조건, 자리만 달라도 3년 기대손익 +34만 vs −1,895만)" |
| "동→블록/건물→매물" 해상도 | "100m 격자 × 서울 전역 25구 — 파일럿 3개 상권이 아니라 전역 커버" |
| PostgreSQL·크롤러 4-Layer 아키텍처 (§5) | 실제 구현: SQLite 단일 DB + FastAPI + React, as-of 재구성·누수 가드 RED→GREEN — **아키텍처 그림을 실물과 일치시킬 것** |
| 가중치: "도메인 규칙 → 지도학습" | E-M 모델 토너먼트 + E-A 피처 가중치 표 (실험 산출물 2장을 그대로 슬라이드로) |

**살릴 것**: §1 문제 정의(정보 비대칭·KB 부실 리스크) · §8 KB 연계(대출 퍼널·컨설팅 증강) · **§이득 ⑥ 여신 심사 보조**("사업이 될 자리인가"라는 심사 축의 부재를 메움 — 발표에서 저평가된 강수) · ⑨ 복제 불가 해자(KB 실매출·상환 이력 = 스케일업 전제) · §9 한계 인정 프레임.

**평가기준 재매핑** (기획안 §10 갱신): 창의성 20점의 축을 "SNS 선행지표"에서 **"검증 방법론(시간분리·누수가드·negative result 공개) + 입지 위험의 가격화(경제성) + 권리금 적정가 리포트(`docs/goodwill-report-design.md` — E6 통과 시 실물, 아니면 설계)"**로 옮긴다. 권리금 서사는 "권리금 실거래 데이터가 세상에 없어서 아무도 못 만들었다 → 수익환원으로 추정가를 만들고, 거래가 쌓이면 시세가 된다 — **KB시세가 아파트에서 밟은 경로를 점포에서 반복**"로 프레이밍. 금지어: "감정가"·"투자의견"·"권리금 담보대출"(→ "KB 적정가 검증 통과 거래에 한한 신용대출 우대"). 기술 적정성 20점은 "ML이 숫자, LLM이 설명" 역할 분리 논리 유지 — 이건 여전히 유효하고 실물과 일치. 임대인 사이드(테넌트믹스·공실 조기경보·건물가치)는 "같은 엔진을 뒤집으면 양면시장" 확장 로드맵 1장.

## 3. LLM 근거 리포트 — 구현 주체 확정 (미정이던 것)

기획안 §5의 "숫자는 ML, 설명은 LLM"은 기술 적정성 점수의 핵심 논리이므로 **실물로 구현한다**. 소유: **레인 B**. `/report` 엔드포인트 — 입력은 실피처·실측치 구조체(그 외 정보 주입 금지), 출력은 문장 3~5개. 실패 시 에러 상태 노출(목업·폴백 금지 정책 동일 적용). 프롬프트에 한계 고정 문장 포함(`ui-spec.md` §S4). 시연 안정성을 위해 데모 영상에는 실호출 장면을 담는다.
